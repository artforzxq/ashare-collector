# A 股个人交易提醒系统

给自己的个人系统：把行情抓下来 → 算状态和关键位 → 只在值得说话的时候提醒你，
并把"结论是怎么来的"全部留痕。Windows 和 macOS 都能跑，双击就有界面。

三条设计原则，改代码前先记住：

1. **分层，每层只有一个出口值**——数据层回答"数据可信吗"，状态层回答"现在是什么市场"，
   机会层回答"值不值得出手"，风险层回答"做多大、错了怎么办"，提醒层回答"要不要打扰你"。
2. **只有一个真相源**——状态只算一次、只存一处，谁都不许自己重算一遍。
3. **默认沉默**——意见不一致时不动；宁可少提醒，不要基于脏数据喊反转。

## 快速开始

启动脚本按平台分开放：Windows 在 `windows\` 里（`.bat`），macOS 在 `macos/` 里（`.command`）。

**每台电脑第一次**：双击 `windows\0-安装环境.bat`（mac 上是 `macos/0-安装环境.command`）。
它不会硬要装一套新 Python——**直接用你电脑上现成的那个**：已经有 `~/ashare-env` 虚拟环境就用它，
没有就直接用系统里的 Python 并把路径记在用户目录（`%USERPROFILE%\ashare-python.txt`）。
这样嵌入式 Python、conda、系统自带的 python3 都能跑，不用先折腾环境。
唯一必须装的是 PyYAML，数据源适配器可以之后再装（`5-安装真实数据源` 那一步）。

然后按顺序双击：

```
0-安装环境      准备 Python 环境（只需一次）
3-每日任务      抓行情 → 算状态 → 出提醒
14-看盘页面     打开本地看盘界面（推荐日常就用这个）
```

数据和代码都在本机，**不联网也能看历史**；只有抓新数据那一步需要网络。

## 自动运行与手机推送

**手机推送**走 [PushPlus](https://www.pushplus.plus)（免费、免账号、扫微信就能用）。
日终任务跑完，系统把当天简报原样推到微信上：状态、关键带、仓位上限、今日提醒、被压制的信号、
数据质量，一个都不少。

token 放哪儿：**别写进 `config.yaml`**（那个文件进版本库）。放在本地文件
`data/pushplus.token`（已被 `.gitignore` 排除，权重 600）里就行，内容就是 token 本身；
也可以改用环境变量 `ASHARE_PUSHPLUS_TOKEN`。三种来源的优先级写在 `collector/notify.py` 顶部。

> **注意**：PushPlus 现在要求账号先实名认证才能发消息，没认证时接口会返回
> `905 账户未进行实名认证`。实名地址：<https://verify.pushplus.plus>。

推送上层的两个设计约定，和整个系统一致：

1. **推送失败不影响任何数据**。行情已经入库、状态已经算完，发不出去只是"今天没打扰到你"，
   任务照常成功，失败原因写在日志里。
2. **同一天只推一次**。`data/last-push.txt` 记着上次推到哪个交易日，周末、节假日重跑日终任务
   不会把同一份简报再吵你一遍；真要重发用 `python run.py push --force`。

**自动运行**（收盘后自己跑）在 macOS 上用 launchd，一步装好：

```
bash macos/24-自动运行.command          # 默认每个工作日 15:35
bash macos/24-自动运行.command 15:50    # 想换时间
bash macos/24-自动运行.command off      # 关掉
```

它做的事就是 `3-每日任务`：抓当日行情 → 算状态 → 出简报 → 推手机，
日志在 `logs/launchd-daily.log`。Windows 那台用任务计划程序跑 `windows\后台-每日任务.bat`
（记得设环境变量 `ASHARE_NO_PAUSE=1`）。

> **macOS 的坑**：launchd 起的任务读不了 `~/Downloads`、`~/Desktop`、`~/Documents` 里的文件
> ——这是系统的隐私保护，报错是 `Operation not permitted`。所以自动运行要求项目**不要**放在
> 这几个目录里，放用户目录下（例如 `~/ashare-collector`）最省事。
> 手动双击启动器不受影响：那是你本人点的，系统会正常放行。

其余操作没有单独的启动器——看盘页面上的「任务卡」能直接跑日终 / 同步 / 筛选 / 快照，
命令行长这样（`python` 指启动器用的那个解释器，双击启动器时不用管）：

| 想干什么 | 用什么 |
|---|---|
| 建库 / 重建（重建前会先备份旧库） | `python run.py init-db` / `python run.py init-db --rebuild` |
| SQL 命令行查库 | `tools\sqlite3.exe data\market.db` |
| 图形化改表（仅 Windows） | 双击项目根目录的 `DB Browser for SQLite.lnk` |
| 装 / 升级数据源（会真取一次数） | `python run.py sources`，升级用 `pip install --upgrade adata akshare` |
| 生成单文件 HTML 简报 | `python run.py dashboard` |
| 生成可发微信的看板图 | `python run.py share` |
| 把当天简报推到手机 | `python run.py push`（`--test` 只发测试消息、`--dry-run` 只演练） |
| 让模型读一遍指标（旁注） | `python run.py analyze SH600487`，另有 `--ledger` / `--backtest` |
| 全市场同步（分批补历史，可中断） | `python run.py sync` |
| 全市场筛选 | `python run.py screen` |
| 观察池候选（谁进谁出） | `python run.py candidates` |
| 历史重放（立刻拿到 5/20 日表现） | `python run.py replay --days 240` |
| 补市场广度（本地 K 线自己算） | `python run.py breadth` |
| 抓当日分时线（盘中跑，只给当天） | `python run.py intraday` |
| 打包数据库 | `python run.py pack` |
| 只重建 5/30/60 分钟聚合（不联网） | `python run.py intraday --aggregate` |

用任务计划程序跑 `后台-每日任务.bat` 时，记得在那个任务里设环境变量 `ASHARE_NO_PAUSE=1`，
否则它会停下来等按键、任务永远不结束。

**这些任务在页面上也能点**，不用回来双击文件——见下一节。

## 看盘页面

双击 `windows\14-看盘页面.bat`（mac 上是 `macos/14-看盘页面.command`），浏览器打开 <http://127.0.0.1:8765>。
**只监听本机**，关掉那个终端窗口就停止服务。

五个视图（顶部栏切换）：**自选标的 / 市场与扫描 / 因子台账 / 参数回测 / 筛选池**。

页面顶部常驻一条**数据状态条**，回答"我现在看到的数字有多新"：
`日线 2026-09-17 ✅当日 · 特征 ✅ · 广度 ⚠差一天 · 分时 11:05 ⏱盘中 · 时段 交易中 · 上次日终 11:18`。
**实时**的只有报价和分时（盯盘区，交易时段每 30 秒自动刷），
**结论类**的数字（状态、趋势分、关键带、仓位上限、广度、涨跌榜）全部是日终算的，
页面按板块标注它们的档位。完整设计见 [docs/页面设计.md](docs/页面设计.md)。

板块划分（每个板块标题上带新鲜度徽章）：

- 自选标的：① 盯盘（实时）→ ② 行情与结论（日终）
- 全市场：① 任务（按需）→ ② 市场概览（日终）→ ③ 涨跌榜（日终）→ ④ 形态筛选（按需）
- 因子台账：① 在册因子（谁在打分、权重多少、覆盖多少天、IC 多少、结论）→ ② 影子因子（离转正还差什么）
- 参数回测：① 参数网格（按 20 日净超额排序，当前配置高亮，带邻域表现）→ ② 怎么读这张表
- 筛选池：① 口径（标的池门槛、回看窗口、上次扫描）→ ② 候选进池 → ③ 池内现状 → ④ 形态表现

后两个视图是只读的：因子台账直接读库里的 `factor_registry` + `factor_contributions`，
回测视图读 `回测/回测结果-*.json`（跑过 CLI 或页面上的「跑一次回测」就会有）。

### 筛选池这一页在回答什么

筛选这条链路有五段，页面以前只露出第三段（形态筛选的名单）。现在合成一页：

| 段 | 做什么 | 页面位置 |
|---|---|---|
| 标的池 | 日线够长 + 近 60 日均成交额过门槛（指数默认不进） | 「① 口径」 |
| 形态判定 | `config.yaml` 里 8 个形态条件表；多标签命中按优先级定主标签 | 「② 候选进池」的形态列 |
| 命中落库 | 每个「筛选日 × 形态 × 标的」一行 | 市场与扫描 →「形态筛选」（原样保留） |
| **候选池** | 按证据排队：能不能建仓 → 反复出现程度 → 流动性；**至少命中 2 次**才算候选 | 「② 候选进池」 |
| **表现回填** | 命中后 5/20 日的实际表现（要跑过 16-信号复盘 / 22-历史重放才有数） | 「④ 形态表现」 |

排序**刻意不做加权总分**——总分会把"命中 3 次的小票"和"命中 1 次的大票"压成一个数，
看的人无从判断哪条证据更硬。三类证据分列开，判断权交回给人；页面上只提供「加入自选 / 移出」两个动作，
机器排队、人点确认。

#### 入池的依据

进候选要同时满足两点：**在池外**，且**至少被命中 2 次**（一次命中是噪声）。排序只用三类可核实的证据：

1. **能不能建仓**：风险层算出来的仓位上限 > 0 的排前面；
2. **反复出现的程度**：出现在几个筛选日、命中几个形态、总共命中几次；
3. **流动性**：近 60 日均成交额，买不进的排后面（门槛与筛选、回测共用 `universe.min_avg_amount_60d`）。

外加一列"命中后 20 日超额"——**要有回填才看得到**（跑过 16-信号复盘 / 22-历史重放）。

#### 出池的依据（只提示，不动作）

系统**从不自动改观察池**。页面上只给两种情况打「考虑移出」：

1. **连续 ≥ `candidates.exit_streak`（默认 5）个筛选日没出现**。用全部筛选日算，不是回看窗口——
   窗口只有 20 天的话，20 天前就没影的票会一律顶格，分不出"刚凉"和"凉很久"。
2. **近 60 日均成交额跌破门槛**——已经买不进，这比形态更有说服力。

但提示要同时满足四个条件才会亮，缺一个就闭嘴：

- 有硬证据（上面两条之一）；
- 是**个股**：基准指数与 ETF 按定义固定配置，不参与轮换；
- **不是持仓**：把实际持仓写进 `watchlist.holdings`，它们不会收到出池提示（去留由仓位决定）；
- **筛选结果够新**：最近一次筛选距今超过 `candidates.exit_stale_days`（默认 5）个交易日就不提示——
  尺子没量准的时候，任何"该出池"都是假警报。

风险层给 0 仓**只显示、不触发**：它说的是"今天别加仓"，不是"这只票不该再跟踪"
（实测里一只上升趋势的票当天也会是 0 仓）。

## AI 指标分析（百炼）

接了阿里云百炼（DashScope），让模型读一遍**本地已经算好的数字**，写一段人话旁注。
用的是 OpenAI 兼容接口，走标准库 `urllib`，没有新增依赖。

**它只接三处，而且全部手动触发：**

| 接在哪 | 喂进去什么 | 不喂什么 | 一次成本 |
|---|---|---|---|
| 自选标的页底部 | 这一只的状态、趋势分、机会分、关键带、仓位上限/止损、因子贡献、提醒、数据质量 | —— | 约 1.0k tokens |
| 因子台账页底部 | **每个因子的汇总**（覆盖天数、IC5/IC20、最大相关、系统给的结论） | 几万行 `factor_contributions` 明细 | 约 1.3k tokens |
| 回测页底部 | **摘要**：样本量/年数/成本/正超额组数 + 前几名与当前配置那行的邻域表现 | 整张参数网格（几百行） | 约 1.3k tokens |

**绝对没有接的地方，以及为什么：**

- 不接进日终任务：每天给观察池每只票都问一遍，一年下来是几十万 tokens，而且大部分日子没人看；
- 不接全市场（哪怕筛选后的几百只也不行）：一次就是几十万 tokens；
- 不接打分、筛选、提醒——这是硬约束，不是省钱：模型的话一旦能改状态分，
  同一份数据两次运行就会得出两个结论，整套审计立刻失去意义。

另外两道闸门：默认**每天最多 20 次真实调用**（`analysis.bailian.daily_limit`，超了直接拒绝，
`--force` 才能绕过），以及每次调用都原样落库（`analysis_log`：提示词、回答、token、耗时）。
提示词里明确禁止给目标价、预测点位和买卖建议，要求"数据不足就直说"。

key 放在 `data/bailian.token`（已被 `.gitignore` 排除，权限 600），或用环境变量 `DASHSCOPE_API_KEY`。
**不要**写进 `config.yaml`。

```
python run.py analyze SH600487        # 单只标的
python run.py analyze --ledger        # 审整张因子台账
python run.py analyze --backtest      # 审最近一次回测摘要
python run.py analyze --all           # 观察池全部（会真的计费，慎用）
python run.py analyze --show          # 只看存过的，不调用
python run.py analyze SH600487 --dry-run   # 只打印要发出去的提示词
```

### 自选标的

- **盯盘条**：现价、涨跌幅、昨收、最高最低、成交额、报价时间。这是**唯一实时**的数字，
  交易时段每 30 秒自动刷新（切到后台就暂停），旁边有手动刷新按钮
- **K 线**：蜡烛图（红涨绿跌）+ MA20/60/120 + 支撑/阻力/区间带 + 提醒标记 + 成交量副图；
  鼠标划过有十字光标和当日开高低收、涨跌、量比、趋势分
- **日K / 分时 切换**：图表上方两个按钮切换。分时是**一分钟一个点**的价格线 + 均价线
  （累计成交额 ÷ 成交量）+ 昨收虚线 + 成交量柱，看的是"今天怎么走的"。
  腾讯的分时接口只给当天，所以打开时如果本地还没有就会现抓一次
  （要联网；断网时给一句提示，不会卡住）
- **顶部指标带**：状态 / 趋势分 / 机会分 / 量比 / 仓位上限 / 止损 / 形态。
  **鼠标移上去就解释"是什么、怎么算、怎么用"**，工具栏的「指标说明」看全表
- **下面三块**：因子贡献（这个分数是谁拉上去的）、关键带（距收盘多远）、本标的提醒
- 左栏底部显示 `本地 N 只 · 有日线 M 只`——一眼知道全市场筛查的火力范围

### 全市场

- **任务卡**：直接点按钮跑日终 / 同步 / 筛选 / 快照 / 抓当日分时，日志实时显示在下方。
 同一时刻只允许一个任务（两个任务同时写库会锁库）
- **市场概览**：涨跌家数、涨停跌停、涨跌中位数、成交额、涨跌分布——**用本地数据算的**，
  会明确标出样本量（本地只补了 40 只时这组数字没有代表性）
- **涨幅榜 / 跌幅榜**：点任意一只直接跳到它的 K 线
- **形态筛选**：见 [全市场筛选](#全市场筛选)

## 数据从哪来

全部是**免费、免账号**的源。实测结论（2026-09，本机网络）：

| 源 | 日线 | 复权 | 北交所 | 说明 |
|---|---|---|---|---|
| **tencent**（主源） | ✅ 约 500 根 | 前复权 | 只给当日 | 走 443，稳定；实时报价可批量问 |
| **sina**（补充源） | ✅ 约 500 根 | 不复权 | ✅ 有历史 | 只给全市场同步当兜底，不进主备交叉校验 |
| baostock（备份源） | 视网络 | 前复权 | — | 走非标准端口 10030；匿名登录按 IP 限流 |
| akshare（兜底源） | 视网络 | 前复权 | — | 日线走东财 `push2his`，部分网络直接断连 |
| adata | ❌ | — | — | 候选函数路径取不到数据，适配器也忽略了 `kind` |

踩过的坑，写下来免得再踩：

1. **别频繁调 baostock 的登录接口**——它按 IP 限流，密集调用会返回"黑名单用户"。
   日终任务已改成"整个进程只登录一次"。
2. **腾讯日线的字段顺序是 (日期, 开, 收, 高, 低, 成交量)**，不是常见的 OHLC；成交量单位是"手"；
   指数返回的键是 `day` 而不是 `qfqday`。适配器里都处理了。
3. **新浪的日线不复权**，所以只在全市场同步里当兜底，免得主备交叉校验天天误报冲突。
4. **成交额分两种口径，看表时要分清**：
   - **日线**：腾讯、新浪的日线接口都**不返回**成交额（实测腾讯三种端点都只有 6 个字段），
     所以 `bars_daily.amount` 是 `成交量 × 均价` 估算的——做量比、z-score 这类相对比较没问题，
     当绝对金额看会失真。指数不做估算（指数的"价格"是点位不是股价）。
   - **分时和实时报价**：这两个接口**给真成交额**（分时的每行带"累计成交额"，报价的字段 35 里
     就写着"价格/成交量/成交额"）。实测：把分时每分钟的成交额加起来，和报价里的成交额
     差 0.01 亿以内（15.17 亿 vs 15.18 亿）。所以 `bars_intraday.amount` 是真值。
   - baostock 的日线也带 `amount`，但它是备份源，用得少。
5. **"缺失"以库里有没有这一天的数据为准**，不是"这次请求成没成功"。
   抓数失败只记 `data_health` 体检记录，不该把已经入库的完整数据判成缺失去冻结提醒。
6. `validation.jump_pct_limit` 默认 11%，会把科创板/创业板 ETF 的真实大涨（上限 20%）
   当成"跳变"阻断，建议按标的类型分别设限。

换网络或换机器，先跑一次 `python run.py sources`——它会**真的取一次数**，而不是只看包装没装。

### 全市场本地化

目标：把全市场的票存到本地，之后**每天只补最新一根**，不用几千次请求。

| 环节 | 手段 | 请求量 |
|---|---|---|
| 代码表 | 几个源**并起来**：新浪（A 股，唯一含北交所）+ baostock（ETF / 指数） | 约 60 次 |
| 历史回补 | 逐只抓，**可中断、可续跑、可分批** | 7000+ 次（分批做） |
| 每日增量 | **一次全市场快照**写成当日 K 线 | 1~2 次 |

代码表里放三类品种，类型按代码段判定，落在 `instruments.type`：
`stock` 个股 / `etf` 场内基金（含 LOF、货基）/ `index` 指数。分工是实测出来的：
**新浪的 `hs_a` 是唯一能拿到北交所的源**（5564 只），**baostock 的 `query_all_stock` 有 ETF 和指数**
（7401 行）但一只北交所都没有，akshare 走东财、在这条网络上直接断连。所以几个源的结果按代码合并，
谁挂了都不影响其余几个——以前这里只认 akshare，它连不上就等于"全市场同步"整条腿断掉。

反复点看盘页面上的「同步全市场」（或跑 `python run.py sync`）就能慢慢填满
（每次约 800 只、7 分钟），已经跟到最新交易日的自动跳过。
每日增量已接进日终任务，由 `warehouse.snapshot_daily` 控制。

**快照只写给观察池以外的股票**：快照价不复权，而观察池的票由日终任务用前复权数据写，
混在同一条 K 线序列里会让均线和突破判断失真。把某只票加进观察池时，系统会用复权数据重写它的历史。

## 决策链路

```
双源交叉校验 → bars_daily（质量标记）
                    ↓
        因子计算 → 层内合成 → 趋势分(0-100)
                    ↓
     迟滞状态机（进入70/退出55，反向30/45，确认2日，最短3日）→ 状态
                    ↓
   关键带（成交量密集区聚类）＋ K 线形态 ─────┐
                    ↓                        │
              机会层：机会分                  │
                    ↓                        ↓
              风险层：仓位上限 + 止损位 ←──────┘
                    ↓
        仲裁 R0-R6（数据健康→风险→状态→机会→提醒）→ 冷却期 → 每日预算 → alerts
```

**状态机**是滞后的（要连续确认 + 最短持续期），这是刻意的——代价是转向慢一两天，
好处是不会被几根 K 线来回打脸。

**关键带**用成交量密集区聚类，产出三种类型：价格下方是 `support`、上方是 `resistance`、
**价格落在带内是 `range`（当前所处区间）**。带宽有上限（4%），
以前没有上限时吐出过"阻力 1.677–1.891"这种宽 12% 的东西——那不是关键位，那是整个成交区间。

**K 线形态**（`collector/candles.py`）补的是均线的滞后：放量长阳/长阴、阳包阴/阴包阳、
锤子、射击之星、向上/向下跳空、站上前 10 日高点、底分型、连阳连阴、十字星。
**至少两个独立信号同时出现才算"反转确认"**，避免单根 K 线就下结论。

**风险层**出口是仓位上限 + 止损位：

1. 数据不可信、跌破支撑/平台下沿、止损离现价超过 8% → **0 仓**
2. 基准仓位按状态给（上升 0.8 / 震荡 0.4 / 下跌 0），再按波动率缩放（目标波动 ÷ 实际波动）
3. **下跌趋势不一票否决**：出现反转确认时允许**试探仓**（上限 0.3）。
   状态机滞后，用它单独否决会永远错过转折第一波——真实案例：科创50ETF 在平台上放量长阳
   +4.27%，状态仍是"下跌趋势"，改用规则后给出 5% 试探仓、止损放平台下沿
4. 止损优先放在**平台/支撑带下沿**（再留 0.5%），没有支撑带才退到 N 倍 ATR
5. 盈亏比达不到 2:1 按比例减仓。**0 仓时不报止损位**——报了会让人以为"有个仓位在那儿"

**仲裁 R0-R6** 把冲突裁决写死在 `arbitrate.py` 里，运行时只做匹配：
R0 数据健康 → R1 风险否决 → R2 状态优先 → R3 默认沉默 → R4 跨周期 → 冷却期 → 预算。
提醒分 P0（立即）/ P1（可操作，每天最多 3 条）/ P2（信息，合并成一条）。

## 复盘与回测

这两个工具回答"这套规则到底有没有用"，都不联网。

`16-信号复盘`：给每条历史提醒补上"之后 5 / 20 个交易日的真实涨跌"
（口径：信号日收盘确认、**次日收盘建仓**、持有 N 个交易日），按级别和信号类型统计胜率；
同时复盘仲裁日志——被压制的信号后来跌了，说明压得对。日终任务会自动回填。
筛选结果走同一套回填：每种形态筛出来的票，之后 5 / 20 个交易日实际涨跌多少，
和同期沪深300 放在一起看——没有参照的"平均涨了 3%"说明不了任何事。

`17-参数回测`：把状态机在历史数据上重跑几十组参数，对比信号次数、5/20 日胜率、**相对基准的净超额**
（基准 = 同一批标的里随便哪天买入，同样扣成本）、信号频率、持有期平均回撤，还有**参数邻域**：
每个组合和它上下左右挪一格的邻居放在一起看。报告存 `回测/回测报告-<日期>.md`。
它用的是**生产代码里同一个状态机函数**，所以回测结论就是实盘行为。

三个口径上的自我约束，少一个结论就会骗人：**可成交性**（建仓日一字涨停买不进、
到期日跌停卖不掉，都不算你的收益）、**成本**（往返佣金 + 印花税 + 过户费，
信号和基准扣同一笔）、**样本**（默认全市场抽样，而不是观察池里那十来只）。

**当前结论**（全市场抽样 400 只、19.7 万根日线，2026-09-17 跑）：基准（随便哪天买、
持有 20 日）是 **+2.77%**，而当前参数（进入 70 / 确认 2 日 / 最短 3 日）的 20 日净超额是
**−1.96%**——跑输闭着眼睛买。36 组参数里只有一组微正（+0.18%），而它邻域均值 −1.00%、
邻居里只有 14% 为正，是典型的**尖峰而不是高原**：那点好看属于抽样噪声，不是找到了有效区间。

所以现在的诚实结论是：**这套状态机还没有被数据证明有效**。真要改参数，
得先等参数空间里出现连成一片、且邻域最差还在 0 以上的区域。

## 全市场筛选

`20-全市场筛选` 用同一套因子体系扫本地全部标的，按形态分组。页面「全市场」视图里能直接看，
点一行跳到那只票的 K 线；报告存 `筛选/筛选结果-<日期>.md`。

扫描前先过**标的池**：历史够长 + 近 60 日均成交额过门槛（`universe.min_avg_amount_60d`，默认 3000 万）。
**指数默认不进这个池子**（`universe.include_index: false`）：它没有成交额可比，拿它过门槛
等于永远免检，抽样时会越占越多，还会把回测的基准带偏。要看指数形态就把它加进观察池，
或者临时加参数 `--include-index`（筛选用 `python run.py screen --include-index`）。
这道门槛是必须的——本地仓库里躺着大量一天只成交几百万的票，它们不是机会，是成交不了、
复权数据也经不起看的噪声，而且常常在事后涨得最猛，放进样本里专门骗结论。
实测本地 5500 只里大约 480 只会被挡在外面。筛选和回测共用同一份门槛（见 `collector/universe.py`），
免得"筛选里排除了、回测里又放进来"。筛出来的票会回填之后 5 / 20 个交易日的真实表现，
所以"这个形态到底有没有用"能拿数据回答，不用凭感觉。

现在有 8 个条件：反转 / 低位横盘 / 蓄势 / 突破 / 放量阳线异动 / 放量阴线异动 / 趋势 / 回踩。

### 多标签：命中几个就是几个，但每只票有一个"主标签"

一只票同时命中多个条件是**常态，也是证据**——既放量又突破，比只突破信息更多。
但同一只票在五个分组里各刷一遍，看的时候就分不清该从哪条开始，所以：

* 底层记录**一条都不删**，`screen_results` 里命中几个条件就存几条；
* 每条条件在 config 里有个 `priority`（数字越小越具体）：突破 10 / 反转 20 / 回踩 30 /
  蓄势 40 / 放量阳线异动 50 / 放量阴线异动 55 / 低位横盘 60 / 趋势 90；
* 一只票命中多个条件时，`priority` 最小的那个就是它的**主标签**：报告里标 ★，
  页面里标「主」。它只回答"从哪一条开始看"，不删任何东西。

有些重叠是结构性的，改不掉也不该改：回踩的定义里就写了 `state == up`，所以
回踩必然全部落在趋势里；突破确认要求量比 ≥ 1.5、异动要求 ≥ 3，所以大突破必然是异动。

异动按阴阳拆成两个条件是刻意的：同样是放量 3 倍，放量长阳和放量长阴的性质相反，
混在一个标签里没法分别统计。**但要说清楚**：277 个交易日的重放数据显示，
两者的后续表现几乎一模一样（20 日超额 −1.78% vs −1.81%）——所以拆开是为了
命名准确、能分开统计，**不是**因为它能把好票坏票分开。

### 观察池怎么维护：谁进、谁出

观察池分两类，规则不一样：

* **指数和 ETF 是固定配置**（`watchlist.indices` / `watchlist.etfs`）。它们是基准和观察工具，
  按定义不轮换——换掉创业板指，状态机就没有参照物了。
* **个股是机会仓**（`watchlist.stocks`）。它不该固定不变，也不该凭感觉换：出现什么就盯什么，
  没有这回事就不该占位置。

`21-观察池候选`（`python run.py candidates`）做"机器能做"的那一半：把筛选结果里的票按可核实的证据排队，
由你点谁进。排序用的三类证据都能从本地数据里查证：

1. **反复出现**——同一只票在多个筛选日、多个形态里被命中。一次命中是噪声，反复才是特征（默认至少 2 次）。
2. **流动性**——近 60 日日均成交额，门槛与筛选、回测共用（`universe.min_avg_amount_60d`）。
3. **历史兑现**——筛出后 20 个交易日的超额收益，有回填才显示，没有就留 `—`。

排序刻意**不做加权总分**：总分会把"命中 3 次的小票"和"命中 1 次的大票"压成一个数，
看的人无从判断哪条证据更硬。所以清单是分列的，判断权留给人。

清单同时打印**池内现状**（每个标的状态、仓位上限、盈亏比、最近一次被筛出的日期），
要不要调出看的是这同一批数字，不是感觉。候选清单本身**不写 `config.yaml`**——
想加谁，把打印出来的那行 `python run.py add …` 复制执行即可（会顺带把历史拉下来）。

池子容量不必硬性设限：个股这一档 20–40 只足够，超过这个数每只分到的注意力比信息量还少。

```yaml
candidates:
  days: 20        # 回看多少个筛选日
  top: 20         # 打印多少条候选
  min_hits: 2     # 至少被命中几次才算候选（1 次是噪声）
```

### 历史重放：今天就能知道"这个形态后来涨没涨"

筛选结果里的 5 / 20 日表现要等**筛出日之后** 20 个交易日才长得出来——今天筛出的票
得等到下个月才知道结果。但历史数据已经在本地了，所以有个更快的办法：
把同一套条件放到**过去每一天**重跑一遍，等价于"那天真的跑了一次筛选"，
唯一的区别是我们已经知道后面发生了什么。这就是 `22-历史重放`（`python run.py replay`）。

**没有未来函数**：每一天用的都是截至那一天收盘的数据（滚动窗口和状态机天生是因果的），
K 线形态也只看到那一天；收益口径和 `16-信号复盘` 完全一致
（信号日收盘确认 → 次日收盘建仓 → 持有 5 / 20 个交易日），所以两边算出来的数字可以直接比。

```
python run.py replay --days 240      # 重放最近 240 个交易日（约一年）
```

跑完会直接打印每个形态的真实表现：条数、5 日胜率与均值、20 日胜率与均值、**20 日超额**
（该形态 20 日均值 − 同期沪深300，按各自的筛选日期取基准）。正数才说明形态本身有信息量。

代价：要把全市场重算一遍，几百秒。特征只算一遍，之后每一天是顺带评估的——
所以"重放 240 天"和"重放 20 天"的耗时差不多。

**注意**：重放会覆盖它覆盖到的那些交易日的筛选结果（先按日期删除再写入），
所以最近一次真实筛选的结果会被同一套条件的重放结果替换——两边本来就应该一致。

### 加一个新形态 = 加一段配置

筛选条件不写死在代码里，全部来自 `config.yaml` 的 `screen.criteria`
（规则引擎在 `collector/rules.py`）。运行时还会同步进 `screen_criteria` 表，
方便以后查"当时用的是哪些条件"。

```yaml
screen:
  min_bars: 80                     # 至少多少根日线才参与
  top: 30                          # 每个条件保留多少条
  criteria:
    - key: 低位横盘                 # 条件名，页面上就是这一列的标签
      title: 跌下来之后横着缩量，等打底  # 一句话说明找什么
      why: 它在均线下方，是打底不是蓄势突破  # 为什么要盯（显示在报告和页面）
      sort: vol_shrink_ratio        # 按哪个字段排序
      desc: false                   # false = 升序（缩量越狠越靠前）
      when:                         # 所有条件是与（全部满足才算命中）
        - {field: consolidation_days, op: ">=", value: 20}
        - {field: vol_shrink_ratio, op: "<=", value: 0.7}
        - {field: close, op: "<=", compare: ma60, factor: 1.0}
        - {field: state, op: "!=", value: up}
```

可用的运算：`==` `!=` `>` `>=` `<` `<=` `between` `in` `not_in` `contains` `startswith` `exists`。
右侧可以是固定值（`value`）、另一个字段（`compare`，可带 `factor` 系数）、或区间（`value: [a, b]`）。

可用字段：

| 字段 | 含义 |
|---|---|
| `state` | `up` / `range` / `down` |
| `trend_score` `opportunity_score` | 趋势分 / 机会分 |
| `close` `ma20` `ma60` `ma120` | 收盘价与各均线（可互相比较） |
| `vol_ratio_20` `vol_shrink_ratio` | 量比（相对 20 日均量）、5 日/60 日量能比 |
| `consolidation_days` | 连续横盘天数（20 日窗口振幅 ≤12%） |
| `breakout_confirmed` | 是否放量突破（1/0） |
| `raw_values.dist_to_level` | 距最近关键带的百分比 |
| `candle.reversal_up` `candle.pattern` | K 线是否反转确认、形态文字 |

改完配置，点页面上的「跑筛选」即可生效（会重新读配置）。新条件会以新标签出现在筛选面板里。

**规则引擎刻意不用 eval**——规则来自配置文件，用 eval 等于把执行权交出去。
取不到值的字段一律判否（宁可漏筛，别把空值当通过），空条件永不命中。

## 因子台账与影子因子

每个因子都登记在 `config.yaml` 的 `factors` 里，带角色（主干 / 修正 / 否决）、
类别、权重、最小样本、`status`（candidate → shadow → active → retired），
运行时同步进 `factor_registry` 表。类别有权重预算（趋势 ≤40%、结构 ≤20%、量能 ≤25%、
波动 ≤15%、资金+情绪 ≤10%），超了会在日终日志里报警。

`19-影子因子体检` 回答规格里准入流程的三个问题：**样本够不够**（影子运行满 20 个交易日）、
**是不是重复指标**（与已生效因子的相关系数 ≥0.7 视为重复）、**有没有独立贡献**
（信息系数 IC：因子值与之后 5/20 个交易日收益的相关性）。

**当前结论**：ADX 是唯一够格转正的影子因子——覆盖 282 个交易日、与现有因子最大相关只有 +0.21、
20 日 IC +0.302（比所有已生效因子都高）。市场广度和 ETF 份额覆盖率是 0，
因为这两个数据源当前取不到数（见[已知问题](#已知问题与下一步)）。

因子贡献默认保留 **500 个交易日**（`collection.factor_keep_days`）——
不然"任意一条提醒都能从贡献表还原"和"影子跑满 20 天"这两条永远达不成。

## 两台电脑（Win + Mac）

项目文件夹可以在两台机器之间拷贝，**运行环境各建各的**（在用户目录里），
所以同步不会坏。唯一需要搬的数据是 `data/market.db`。

macOS 上用 `macos/` 里同编号的 `.command`（双击即可），Windows 用 `windows\` 里的 `.bat`；
两边的启动器调用同一份逻辑，不会各改各的。详细步骤、注意事项、故障排查见《两台电脑怎么用.md》。

### 把数据库整个带走

跑 `python run.py pack`（这一步没有单独的启动器），它会：

1. **先抢一次写锁**——如果 DB Browser / 看盘页面 / 某个任务正在用它，直接拒绝并让你先关掉。
   这样拿到的才是一致的快照，而不是写了一半的库。
2. 做一次 `PRAGMA quick_check` 完整性检查。
3. 压缩输出到 `备份/market-<时间戳>.zip`，里面是 `data/market.db` + 一份 `README.txt`
   （写明打包时间、标的数、日线数、怎么还原）。

拿回去之后：解压，把 `market.db` 放回项目的 `data/` 目录（覆盖同名文件），
双击 `windows\14-看盘页面.bat` 就能看；想继续抓数据就双击 `windows\3-每日任务.bat`
（mac 上换成 `macos/` 里的同名文件）。

参考体积：5500 只票、269 万根日线 ≈ **491 MB**，压完 **139 MB**，耗时约 15 秒。
（微信传文件有大小限制，建议用 AirDrop / U 盘 / 网盘。）

**为什么整包搬是安全的**：SQLite 是单文件、内部不存绝对路径，Windows 和 Mac 通用；
这个库用的是普通日志模式（不是 WAL），没有 `-wal` / `-shm` 旁挂文件，
所以停掉写入之后直接复制就是一致的。同步进度也全在这个文件里——
另一台电脑上继续点「同步全市场」，会接着你没补完的部分往下走。

## 已知问题与下一步

**最重要的那条：筛选出来的形态，没有一个是正超额的。**

`22-历史重放` 把同一套条件放到 2025-07-24 → 2026-09-18 的 277 个交易日上重跑了一遍
（约 4.9 万条命中、5.0 万个样本），每个形态的 20 日表现都跑输"同一批日期里随便买一只
同口径的票"（全市场等权基准 +0.71%）：

| 形态 | 样本 | 20 日均值 | vs 沪深300 | vs 全市场等权 |
|---|---|---|---|---|
| 回踩 | 7377 | −0.06% | −0.63% | **−0.77%** |
| 低位横盘 | 5554 | −0.16% | −0.23% | **−0.87%** |
| 趋势 | 7603 | −0.32% | −0.82% | **−1.03%** |
| 放量阳线异动 | 7233 | −1.07% | −1.16% | **−1.78%** |
| 放量阴线异动 | 5785 | −1.10% | −1.12% | **−1.81%** |
| 突破 | 7281 | −1.19% | −1.40% | **−1.90%** |
| 反转 | 7321 | −1.67% | −2.08% | **−2.38%** |
| 蓄势 | 355 | −1.61% | −2.36% | **−2.32%** |

沪深300 同期 +0.57%、全市场等权 +0.71%，两者只差 0.14%——所以这不是"这批票整体不如大盘"
的贝塔问题，是形态自己没判断力。而且越"热闹"的形态（反转、突破、放量）越差，
越安静的（回踩、低位横盘）反而没那么差，方向上更像是**追热点在短周期里被收割**。

结论：**这套筛选条件目前只能当"看什么的清单"，不能当"买什么的信号"。**
要变成信号，得先有正超额的形态出现——在那之前，任何阈值微调都是在没有基准的情况下瞎调。

**当前取不到数的地方**（不是代码问题，是这些接口在这条网络上不通）：

- **市场广度**：已改为**用本地 K 线自己数**（`python run.py breadth`）——东财 `82.push2`
  那条接口在本机网络上连 DNS 都解析不了，而本地已有沪深京全部个股的日线，涨跌家数、
  涨跌停家数、中位数涨跌幅都能自己算，样本数记在 `market_breadth.coverage` 列里，
  少于 1000 只就不写入（宁可空着，也不把 99 只票当成全市场）。
- **ETF 份额 / 融资融券**：上交所 `query.sse.com.cn` 不通，券商接口也没接。
- **分钟线 / 跨周期**：分时线（`bars_intraday`）现在能抓了，而且**同时存 1 分钟和聚合出来的
  5 / 30 / 60 分钟**（同一张表，靠 `period` 字段区分）。但原始数据**只有当天**——
  腾讯那个接口不给历史分钟线，所以得在盘中跑（点看盘页面上的「抓当日分时」，
  或者 `python run.py intraday`），跑一次攒一天，保留最近 250 个交易日。
  聚合口径按 A 股约定：一天 240 个可交易分钟（上午 09:30–11:29、下午 13:00–14:59），
  11:30 和 15:00 的收盘打印并进各自时段最后一根，所以 30 分钟正好 8 根、5 分钟 48 根。
  规格里"日线优先于 30 分钟"那条仲裁规则**仍不触发**：30 分钟线有了，但还没有基于
  分钟线的状态判断，规则缺的是输入端而不是数据。

**还没做的功能**：

- 推送只走 PushPlus 一条路，还没有企业微信机器人 / Server酱 这类备选通道
  （要加的话照 `collector/notify.py` 的 `send()` 再写一个发送函数即可）
- 因子准入流程的自动化（相关性检验、样本外验证已有工具，还差"影子运行满 20 天自动提醒转正"）
- 观察池批量导入（现在页面一个一个加，或 `python run.py add 600519 000001 ...`）

**已知的小毛病**：

- 腾讯/新浪不返回成交额，用成交量×均价估算；指数的量能退回用成交量计算。
- `jump_pct_limit` 一刀切 11%，详见[数据从哪来](#数据从哪来)第 6 条。
- 涨跌停判定是按"前收盘价 × 幅度"推的，板块看代码前缀（主板 10% / 创业板科创板 20% /
  北交所 30%），ST 从名称里认。库里 `instruments.board` 和 `is_st` 目前都没填，
  上市日期也是空的，所以**新股上市首日不设涨跌幅**这条识别不了，这类票会被当普通票处理
  （通常已经被小票门槛挡在外面；要更准就得先把代码表补齐）。
- **akshare 装不上不一定是网络问题**：它依赖的 `jsonpath` 只发布源码包，而那份源码包的
  `setup.py` 第一行就 `import jsonpath as module`（拿自己读版本号），pip 的隔离构建环境里
  源码目录不在 `sys.path` 上，于是必然 `ModuleNotFoundError: No module named 'jsonpath'`。
  仓库 `tools/vendor/` 里放了一个 wheel：`jsonpath.py` 原文一字未改（MD5 与官方 sdist 一致），
  只把打包脚本改成按文件路径加载。手动装就把它一起写进命令：
  `python -m pip install "tools\vendor\jsonpath-0.82.2-py3-none-any.whl" akshare baostock`；
  `windows\win-run.bat` 的安装步骤已经内置这个兜底，正常装失败会自动带上它重试。
- 改了后端代码必须**重启服务**（Python 模块只在进程启动时加载），
  页面上的 `/api/health` 会提示"服务比代码旧"。

## 设计约束

改代码前先读这几条，它们是这套系统能保持"只有一种声音"的原因：

1. **每层只能有一个出口值**，层内因子必须先合成再上行。禁止把多个因子各自送到提醒层。
2. **状态只算一次、只存一个字段**（`features_daily.state`），任何模块都不许自己重算。
3. **因子角色在 `config.yaml` 里登记**，运行时不能改。
4. **新因子走准入流程**：相关性 < 0.7 → 样本外验证 → 影子运行 20 个交易日 → 转正。
5. **改权重或规则后必须更新 `project.feature_version`**，否则历史信号无法解释。
6. **所有写入按主键 upsert**，任何任务都能全量重跑而不产生重复数据（仲裁日志也已幂等）。
7. **测试自带输入**：测试不许依赖 `config.yaml` 里的活配置（观察池是用户会改的）。
