# 数据源对照：`a-stock-data` 能给我们补什么

核实时间：2026-10-09。被对照的项目：[simonlin1212/a-stock-data](https://github.com/simonlin1212/a-stock-data)。

## 一、它是什么（核实过的）

| 项 | 值 |
|---|---|
| 仓库 | `simonlin1212/a-stock-data`，★10,710，Apache-2.0，Python |
| 活跃度 | 2026-05-11 建，最近提交 2026-10-07（V3.10.1） |
| **PyPI 上有没有** | **没有**。`a-stock-data` / `astockdata` / `a_stock_data` 三个拼写都查不到 |
| 实际形态 | 一份 **433 KB 的 `SKILL.md`**（结构化 Markdown + 内嵌 Python），面向 AI 编程助手（Claude Code / Codex / OpenClaw） |
| 依赖 | `pip install mootdx requests pandas stockstats numpy baostock xlrd openpyxl` |
| 规模 | 15 层 · 87 个能力入口（82 主 + 5 备胎）· 34 个来源 · 除 iwencai 外零鉴权 |

**它不是数据源，是一份"34 个源 × 87 个端点"的整理**。所以"能不能用"要分三层看：当参考手册（立刻可用）、
当能力的补充源（要摘代码）、当主源（不建议）。

## 二、一句话结论

**最该摘的不是那些我们没做过的新层（研报/舆情/期货），而是给三个"孤儿能力"补上第二个源**——
我们的 `lhb`（龙虎榜）、`fund_flow`（资金流）、`margin`（融资融券）**只挂在 akshare 一个源上**，
而 akshare 在这条线路上长期连不上（东财 `push2his` 被切）。它正好为这三个各整理了一个
**不同域名、不同风控面**的独立备胎。

## 三、我们的家底：8 个能力，3 个是孤儿

能力路由在 `collector/sources/`：`_source_for(pool, "<能力>")` 按 主源 → 备份 → 兜底 → 补充源
依次找第一个实现了该能力的适配器。所以**只要有一个适配器实现了某个能力，路由会自动用上它**。

| 能力 | 谁实现了它 | 在这条线路上能用吗 |
|---|---|---|
| `daily_bars`（日线/前复权） | tencent、sina、baostock、akshare、adata | ✅ tencent 稳定 |
| `market_snapshot`（全市场快照） | tencent、akshare | ✅ tencent |
| `intraday_bars` / `intraday_snapshot` | tencent、akshare | ✅ tencent（但只有当天） |
| `trade_calendar` | tencent、baostock、akshare | ✅ |
| `etf_shares` | **sse、szse**、akshare | ✅ 交易所官方 |
| **`lhb`（龙虎榜）** | **只有 akshare** | ❌ **孤儿** |
| **`fund_flow`（资金流）** | **只有 akshare** | ❌ **孤儿** |
| **`margin`（融资融券）** | **只有 akshare** | ❌ **孤儿** |

这三个孤儿不是"没写代码"，是"写了代码但上游连不上"——`python run.py flows` 和 `python run.py margin`
在这台机器上会静默地拿不到数据。

## 四、重合的部分：三条原则互相印证

它的 README 里有三条判断，和我们自己踩坑后定下来的完全一致：

| 它的说法 | 我们的对应 |
|---|---|
| 「能用腾讯 / 交易所官方，就别用东财」「东财只用于独有数据，已内置限流防封」 | 我们的 `config.yaml`：主源 tencent、补充源 sina/sse/szse；东财接口在本地实测被切 |
| 「除 mootdx 与 baostock 外，全部直连 HTTP API，不经第三方数据封装」 | 我们的适配器就是直连 HTTP/TCP，没有中间封装层 |
| 「腾讯 K 线成交量单位：科创板（688/689）是股，其余是手」（V3.10.1 更正） | 我们 2026-09-19 修过同一个坑（`tencent_source._volume_multiplier`），库里有 11 万行曾被污染 |
| 「主源被封时降级」「并非所有能力都有备份，取数后仍须检查日期与完整性」 | 我们的 `_source_for` 路由 + `validate.py` 的双源交叉校验（但只覆盖日线） |

第四条正是我们的短板：**我们的降级只对日线做过**，另外几个能力要么没有第二源，要么只有一个源。

## 五、增量清单（按"值不值得摘"排序）

### 1. 三个孤儿能力的官方/独立备胎 ★★★★★

| 它整理的备胎 | 补我们哪个孤儿 | 代价 |
|---|---|---|
| 官方龙虎榜备胎：上交所 + 深交所官方接口，零鉴权，含营业部席位 | `lhb` | 一个适配器，两个端点；官方接口字段要自己拼 |
| 资金流备胎：新浪日度四档单净额（超大/大/中/小单 + 净流入） | `fund_flow` | 一个端点；只有日度，没有分钟级 |
| 官方两融备胎：上交所/深交所分开查询（金额元、余量股/份） | `margin` | 两个端点；上交所缺融券余额金额时留空 |

**为什么排第一**：这三个能力现在是"有接口、没数据"。补上之后我们有两个独立来源可以互相核对，
而路由层不用改一行代码（实现方法名对上就行）。

### 2. 通达信盘后包：一次拿全市场某天日线，**含真成交额** ★★★★★

- 我们的痛点：全市场补历史是**一只一个请求**——今天实测 800 只 / 6.3 分钟，
  7700 只要一个多小时；而且腾讯日线**不返回成交额**，`bars_daily.amount` 是"成交量 × 均价"估算的
- 它给的：某交易日沪深北全市场日线，**含成交额**，单个 zip 约 2~3 MB
- 代价：要解析盘后包格式（二进制/zip）；依赖 mootdx 或自己解；只到收盘后才有；
  2022-05-06 之前没有北交所；它自己注明"未逐日验证哪些日期还有包"
- 判断：**省下的是"每次全市场同步一个多小时"**，而且能校准我们的估算成交额——这条最值

### 3. 新浪复权因子（qfq / hfq） ★★★★

- 我们的痛点：日线是前复权，但从没有独立来源核对**复权因子**本身。双源校验只比收盘价与涨跌幅，
  除权日口径不一致时只能记一句"复权基准不同"（`validate.py`）
- 它给的：因子序列 + 套用到不复权 K 线的方法
- 代价：一个 HTTP 端点
- 判断：能让"除权日"从"记说明"变成"真对账"

### 4. 历史分钟线（腾讯 K 线 1/5/15/30/60 分钟） ★★★★

- 我们的限制写在 README 里：**"腾讯那个接口不给历史分钟线，所以分时只有当天"**
- 它给的：腾讯 K 线的三个入口轮换，声称支持 1/5/15/30/60 分钟
- 判断：**先验证再动手**——如果腾讯真能给历史分钟，我们那条限制就解除了；
  它自己也说"三个入口轮换"，说明单入口有限流

### 5. 逐笔成交 + 盘后完整性核对 ★★★

- 它给的：最近一个交易日全部分笔（时间/价格/量/额/买卖方向），
  以及**收盘后用当日成交额核对完整性**的做法
- 判断：逐笔数据我们暂时用不上，但"用成交额核对当天数据完整性"这个**校验思路**值得先学

### 6. ST 名单 / 上市退市日 / 估值历史（PE/PB/PS + 换手率 + 停牌 + ST） ★★★

- 我们的已知问题：`instruments.board` / `is_st` / `listed_date` 一直是空的，
  涨跌停判定靠代码前缀，ST 从名称里认，新股首日不设限识别不了
- 它给的：ST 当日名单（东财不可达时退 baostock）、上市退市日（唯一零鉴权退市日源）、
  日频估值历史（含停牌与 ST，可回溯 2016，**不支持北交所**）
- 判断：能把我们"已知的小毛病"里那几条一次性补齐

### 7. 打板层（涨停/炸板/跌停池、连板、封板资金、首末封板时间） ★★

- 我们现在用本地 K 线自己算涨跌停家数与连板（`breadth.py` + `board_streak` 影子因子）
- 它多的是**本地算不出来的**：封板资金、炸板次数、首末封板时间（要靠盘口/逐笔）
- 判断：等要做"打板情绪"那一层时再摘

### 8. 我们完全没做的层：可转债 / ETF 期权 / 期货大宗 / 宏观利率 / 事件驱动 / 财务公告研报舆情 ★~★★

这些属于"再开一层"，和现在的机械决策链正交。要做的时候它是现成的入口清单
（可转债 1 个端点、ETF 期权 3 个、期货大宗 7 个、宏观利率 6 个、事件驱动 6 个）。

## 六、不建议接的

| 不接 | 为什么 |
|---|---|
| 当主源或备份源 | 它的行情层上游和我们**高度重合**（腾讯/新浪/东财/baostock/通达信）；我们真正的痛点是**网络级**的，换一层封装照样断 |
| 整包引入（87 个端点） | 它不是可 import 的库，要用只能把内嵌代码摘进适配器，**维护责任就转到我们这边**；而且它没有版本化 API、没有测试契约 |
| 东财系端点 | 我们这条线路上 `push2his` / `82.push2` 被切，它也没解决（只是换了调用姿势）——除非同时上它的限流与会话复用 |
| 研报 / 新闻 / 舆情 | 和"机械决策链"正交，现阶段加进来只会增加维护面 |

## 七、建议的动作（按顺序）

1. **先补三个孤儿能力**（龙虎榜 / 资金流 / 融资融券的官方或独立备胎）——它们是"有接口没数据"，
   补上立刻见效，路由层零改动
2. **再评估通达信盘后包**——它能把"全市场同步一个多小时"压到"一次一个 zip"，
   而且给的是真成交额（我们现在是估算）
3. **顺手验证两件事**：腾讯 K 线能不能给历史分钟线；新浪复权因子能不能和我们的前复权对账
4. 以上都做完、也确实需要新层了，再谈可转债 / 期权 / 事件驱动

接入方式固定：在 `collector/sources/` 写一个适配器 → 声明它实现哪些能力 → 挂到
`config.yaml` 的 `sources.extra`（补充源，**不要动 primary/backup**，那两个参与双源交叉校验）
→ `python run.py sources` 真取一次数 → 用 `27-单票体检` 对口径。
